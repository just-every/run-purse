# Purse acceptance

Target edition: 17 October 2026. This checklist covers the complete `CONTRACT.md` destination: connected procurement that replaces Procurify for growing US businesses. Clause IDs are stable and match `CONTRACT.md` one for one. Each entry gives the clause's acceptance journey and its status at commit `9f201c00eba7aecadf9239e1205f6933a0dd1cb6` (the supplied code audit was taken at `dc2ae705c3cdd9c82a2345ca35db6f6c99a60d58`; no domain source or domain test changed between them). Done means the bounded local journey passes on the cited code and tests; it does not establish hosted placement, provider receipt, a real owner export or pilot acceptance. Counts: 18 done, 35 partial, 58 missing.

Journeys run through public doors: the native-session HTTP API, the browser at 1440 and 390 pixels, the RER command path, and the supplier and approver links, email, Slack, Teams and native apps the clauses name. Fakes are allowed only at the paid or network edge (mail delivery, Slack and Teams, PunchOut catalogues, BILL, QuickBooks Online, QuickBooks Desktop Web Connector, Xero, NetSuite, Sage Intacct, Business Central, Ramp, Brex, the Procurify API, carriers, screening and bank-verification providers), and provider journeys pass against each provider's own sandbox before a clause is marked done. Use synthetic US business data in USD. Do not weaken existing assertions to satisfy a clause; prove one-off fixes with before/after cases outside the permanent suite. CI remains the full verification wall.

## How the current journeys run

`tests/purse.test.mjs` is a business-flow suite, with actual native sign-in and real workerd/D1, no fake application database; its tests are named P01 to P17 after the PUR clauses. `tests/browser.mjs` runs the fresh-install human journey at 1440 and 390 pixels and records screenshots, downloaded PO documents and complete archives in a private evidence directory. Default runs use genuine local Git clones of committed HEAD, without inherited dependencies, settings or data. Uncommitted changes are not included. GitHub Verify runs the integrated wall and these clone journeys from its exact checkout. Exact-commit CI status is recorded by the GitHub run.

Run `pnpm test:purse` and `pnpm typecheck` for focused domain checks. Run `node tests/browser.mjs` for the full browser and CLI proof, optionally setting `PURSE_EVIDENCE` to a private output directory. Its `--source-copy` option explicitly tests precommit author copies, with that qualification in its result; default runs still clone committed HEAD. Its `--archive-only --existing` mode proves only archive operations on an existing fixture installation; its empty journey list must never be presented as fresh-install browser proof. `rer verify` is the final integrated wall and belongs to CI/final review.

Known physical limits are explicit: attachments currently accept 1 MB per file; requests accept 100 lines; reviewed fixture CSV batches accept 300 records, advancing 20 rows per atomic batch and at most two batches per request. Resume is explicit. These are visible limits, not hidden truncation. Imported data is inert and retains original statuses; native approval is required for new purchasing.

The owner has not supplied an anonymised purchasing case, an actual Procurify account's Export Data CSVs or API access, or a current-process baseline. All development examples are synthetic test fixtures; IMPORT-001 and pilot economics require real owner input. Existing installations retain applied migrations; the forward upgrade and same-release archive restore path is described in `UPGRADING.md`.

## Backup and upgrade

A pre-upgrade export restores only with the Purse release that made it. Restore it
into an empty installation of that release, upgrade that installation’s source
in place, run `rer install` and `rer setup` inside that existing checkout, then export again. Keep the original release
and private export until recovery is verified. Never import an older release’s
archive directly into the current release.
